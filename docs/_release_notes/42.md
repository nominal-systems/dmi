## Behaviour changes

Both come with DMI API [#410](https://github.com/nominal-systems/dmi-api/pull/410).

- **An identical redelivery no longer notifies the PIMS.** When a provider delivers a result or an order that DMI already has, with nothing changed, DMI no longer saves it again and no longer sends `report:updated` or `order:updated` for it. Event payloads keep their shape. To send a report to the PIMS again on purpose, use the admin republish action (`POST /admin/reports/:reportId/republish`).
- **A withdrawn interpretation is now cleared from the stored report.** When a delivery has no interpretation for an observation that has one stored, the stored one is now cleared, so reading the report returns `null` for it. Until this release the stored value stayed, while the `report:updated` for that delivery already went out without it.

## How to test in the admin UI

Four of this release's changes can be checked by hand in the admin UI. The DMI API serves it under its `/ui` path. It shows no version number: the "Search by Accession ID..." box on External Requests is the sign that the environment runs this release.

### 1. Find one order's requests by accession ID

DMI Admin UI [#147](https://github.com/nominal-systems/dmi-api-admin-ui/pull/147), DMI API [#407](https://github.com/nominal-systems/dmi-api/pull/407).

**You need:** the accession ID of an order placed in that environment, and the day it was placed.

1. Open **External Requests**.
2. Set **Date** to cover the order's day, and tick **2xx** under **Response Status**. The page opens on today's 4xx and 5xx only, so an order whose requests all succeeded shows nothing until you do.
3. Type the accession ID into **Search by Accession ID...** and press Enter.

**Expect:**

- Only that order's requests are listed, and the page address ends in `?accessionId=…`.
- Typing the ID in lowercase or in uppercase gives the same rows.
- Reloading the page keeps the search. **Clear** or Escape removes it.
- The search combines with the provider, status, method, practice and date filters.

**Before:** the page had no such box, and one order's requests could not be listed.

**Also changed:** on a narrow window the toolbar's controls now move to a second row. Before, some sat on top of each other or off the screen, on External Requests, Integrations and the Dashboard.

### 2. External Requests opens on a busy day

DMI API [#408](https://github.com/nominal-systems/dmi-api/pull/408).

**You need:** a date range with more than 1,000 requests. One busy day is enough in production; a test environment may need a longer range.

1. Open **External Requests**.
2. Pick the date range and tick all four of **2xx**, **3xx**, **4xx** and **5xx**.

**Expect:**

- The page loads and the line under the table reads "Showing 1-20 of **1,000+**".
- Narrow the filter until fewer than 1,000 match, for example to **5xx** only, and the line shows the exact number again.

**Before:** the total was always counted exactly. In production that count has made this view fail with an error, for example on a full day with all four statuses ticked.

If the range holds fewer than 1,000 requests, the exact number is the right result, and the cap cannot be seen.

### 3. Map a breed that sits late in a provider's list

DMI Admin UI [#146](https://github.com/nominal-systems/dmi-api-admin-ui/pull/146).

**You need:** a provider with more than 500 breeds. Antech V6 has 758 in its development catalogue.

1. Open **Reference Data**, go to **Breeds**, and click **Edit** on a breed whose Antech V6 mapping is not set.
2. Under **Mappings**, click **Set** on the Antech V6 row.
3. Type a name from the end of the alphabet into the search box, for example `Yorkshire`.

**Expect:** the breed is listed (with Antech V6's development catalogue: `Yorkshire Terrier [190]`) and can be picked.

**Before:** "No results found". The search only knew the first 500 entries in name order, so about a third of Antech V6's breeds could not be mapped from the UI.

Picking an entry only queues the mapping. Close the editor without saving unless the mapping is meant.

### 4. Events shows the practice on every row

DMI Admin UI [#143](https://github.com/nominal-systems/dmi-api-admin-ui/pull/143).

**You need:** an environment with more than 1,000 practices to see the difference. On a smaller one this is a check that nothing broke.

1. Open **Events**.
2. Page through a few pages, and change the date range or a filter.

**Expect:** the **Practice** column is filled, also for events of practices that were set up long ago.

**Before:** the page fetched the 1,000 most recently created practices on every load. With more than 1,000, an event of an older practice showed an empty Practice column.

For a closer look, the browser's network tab shows the lookup: `GET …/admin/practices?page=1&limit=1000&ids=…` now carries `ids`, the practices of the rows on the page. Before, it had no `ids`.

**How this was built**

- Ranges are PROD-to-PROD: every commit between the version production is running and the version replacing it, including releases that only ever reached DEV, QA or UAT.
- Bundled components are resolved by reading the version pinned in the parent at each tag. For npm dependencies that is `package-lock.json` (what actually shipped), falling back to the `package.json` range.
- DMI Admin UI is not an npm dependency: it is resolved from `.github/workflows/build-and-push-to-registry.yml` in DMI API at each tag - the tag the build workflow checks out, builds and copies into the DMI API image, so it reaches PROD with the DMI API version that pins it.
- Change types come from, in order: conventional-commit prefix, PR label, branch prefix. Anything with none of those lands in **Changes** rather than being guessed at.
